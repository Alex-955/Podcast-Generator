# 播客生成器：改进路线图与双会话分工

日期：2026-09-22（GMT+8）  
性质：跨会话任务交接。本文是推进建议与首批任务范围，不代表所有后续功能均已获准实施。  
更新：2026-09-26（GMT+8）。阶段现状与后续建议见 [9 月 26 日检查与分工](project-status-and-next-steps-2026-09-26.md)。以下职责与文件所有权已按用户最新说明调整；历史首批问题不代表仍全部未修复。

## 1. 目标与需求依据

产品目标：把文章转换为忠实原文、容易理解、能够稳定收听的双人播客。双人形式服务于理解，不以对话轮数、音乐或视觉动效作为质量证明。

已核对的用户要求：
- 2026-09-18，「文章转双人播客」会话第 14 轮：需要看到卡在哪个阶段；MVP 先在本地播放，不急于导出；移动端后续再做；Edge-TTS 听感不够自然，愿意考虑付费 TTS。
- 同会话第 16 轮：需要缓存，希望避免重复等待；商业 TTS 希望先试听再选择。
- 2026-09-22，当前会话：要求总结方案，由第一个历史会话做 UI 设计，第二个历史会话做代码执行与 Bug 修复。

据此修正本会话上一轮建议：移动端、跨设备、导出及复杂混音不进入首批；商业 TTS 是待试听与预算确认的候选，不默认继续坚持免费接口，也不默认选择供应商。

需要区分两种缓存：
1. 播放缓存/持久化：已经生成的音频可回退、重播、刷新后重新打开，不重新调用 TTS。
2. 合成缓存：重试或改动剧本时，未变化的片段可复用。
当前完整音频播放器的正常回退并不需要重新合成；不能把用户对重复等待的担忧写成已复现的回退缺陷。

## 3. 文件所有权与协作机制

- A 的设计文件为 `design/`、`plan/ui/`；设计确认并批准接入后，`public/` 下前端源码由 A 唯一维护。`public/podcasts/` 等生成产物不属于样式改造范围。
- B 维护 `server.js`、`src/`、后端测试与 `plan/engineering/`；不再修改 `public/` 前端源码。依赖文件由 B 协调维护，涉及前端依赖先对齐，不默认引入新框架。
- 本路线图及两份任务书由当前协调会话维护。执行者有异议时在自己的报告里列出，不自行同时改共享任务书。
- A 的样式设计与 B 的后端收尾可并行。正式迁移时 A 保留已有输入来源、互斥与过期响应保护，不能用 Mock 原型整份覆盖 `public/app.js`。
- B 提供 `plan/engineering/api-contract.md`，A 在状态联调前核对。接口发生变化，由 B 修改契约并列出兼容影响。
- 同一项目目录不允许两个会话同时编辑同一文件；前端测试（现有 `test/inputSource.test.js` 及后续 UI 测试）归 A，后端测试归 B，联合 E2E 需先指定负责人。
- UI 方案通过用户审阅、接口契约达成一致后，由 A 接入生产前端，B 只提供接口与后端支持；协调会话独立验收。分工确认不等于自动批准集成或 B1 全部功能。

## 4. 推进顺序与阶段关卡

### 阶段 0：正确性基线＋UI 主流程设计（首批，可并行）

A：设计桌面 Web 的「输入 → 解析确认 → 生成状态 → 播放」主流程，提供正常、失败、恢复三条可演示路径。

B：先复现并修复输入串线、抓取重试、输入/输出结构校验、TTS 超时生命周期和音频时间轴问题；建立离线回归测试；评估安全整改。不要在这一批顺便重写框架或完成整张路线图。

关卡：
- 已列问题有复现和回归证据，不能只给“已修复”结论。
- A 原型明确哪些是模拟数据；完成用户审阅后再集成。
- 安全整改不得继续扩大访问边界；需要调整证书信任或服务访问方式时先说明影响并确认。

### 阶段 1：真实进度＋可恢复任务＋缓存

阶段 0 验收后启动。

- 后台任务与单次 HTTP 请求解耦，任务有稳定 ID。
- 每阶段持久化正文、剧本、片段完成状态和最终音频；不把 API Key 写进任务、日志或公开元数据。
- 提供真实阶段、阶段耗时、已完成片段数、重试信息及可操作错误。
- 先用轮询即可，不把 SSE 作为前置要求；未观测到总量时显示阶段与耗时，不伪造百分比。
- 支持刷新后恢复任务查看、失败后继续、重复请求去重。
- 合成缓存键覆盖文本、Provider、模型/版本、voice、语速及实际生效的声音配置；缓存命中需校验产物完整。
- 保留简单历史/最近任务入口，以便找回当前及已完成作品；不发展成复杂内容管理系统。

验收：模拟第 N 段失败，续做不重新生成已持久化剧本和有效音频；刷新后状态可恢复；重播不调用 TTS；只改一段时复用其余有效片段；服务重启后不会永远显示 running；取消后无孤儿写入。

### 阶段 2：可信剧本＋声音质量选择

两条路径可独立评估，实施前各自确认范围。

内容路径：
- 阶段 0 先加入基本忠实性约束，明确原文是待处理数据、不是可覆盖系统规则的指令。
- 此阶段进一步采用「带来源提纲 → 对话 → 关键事实核查」，保留数字、条件、作者观点与不确定性。
- 长文不再仅截前 12,000 字；按章节处理并核查关键点覆盖。
- 双人分工是提问/追问与解释/证据，不强制制造冲突或无依据的新观点。
- 在小样本中验证，再决定是否增加时长/理解深度选项；不先堆风格。

声音路径：
- 用户先试听 MiniMax、百炼 CosyVoice 等候选；模型、价格、配额和接口能力需按实施时官方资料重新核实。
- 同文、接近语速与音量的样本进行比较；官方演示不能代替整条生成链路实测。
- 经用户确认 Provider、计费和凭据方式后，先接一个商业 Provider。没有配置时明确提示，不自动切换到收费 Provider。
- 若 Edge-TTS 持续阻塞核心可用性，可提前该选择关卡，而不是无限追加重试。
- 付费服务不能保证完全消除网络故障，任务恢复和缓存仍必须存在。

验收：固定文章集检查事实、关键点、限制条件与理解效果；记录真实成本及延迟；将听感评价与工程成功率分开报告。

### 阶段 3：稳定 Web 后的体验扩展（暂缓）

依据实际使用情况再选择：更完整的历史与播放位置恢复、移动端收听、锁屏控制、待听队列、流式首段播放、分享/导出、真实 BGM 混音。

不在当前阶段承诺 PWA、跨设备同步或公网部署。已有基本下载功能不必为了“暂缓”而删除。

## 5. 当前事实与需要纠正的历史结论

下列为本总结会话在 2026-09-22 的本地检查，执行前仍应复核代码是否变化：

| 观察 | 证据 | 性质 |
|---|---|---|
| 链接页可优先发送旧正文，忽略新 URL | `public/app.js` 的 `getCurrentInputContent` 与 `url: content ? '' : url` | 本地 DOM 桩复现 |
| 第二次抓取的长正文无法替换第一次非空短正文 | `src/services/extractor.js` 的 `lastContent = lastContent || content` | 用两次 mock 响应复现 |
| 对象台词被转换成 `[object Object]` | `src/services/scriptEngine.js` 的 `String(item.text || '')` | 本地调用复现 |
| 0.35 秒间隔在现有格式下实际生成 0.36 秒 | `mp3Utils.js` 整帧取整，与 `ttsService.js` 时间累加 | 本地帧解析核验，20 段仅间隔项约差 0.19 秒 |
| TTS timeout 不涵盖连接阶段，超时不清理连接/流 | 当前 `node-edge-tts/dist/edge-tts.js` | 依赖源码核验，未做本轮在线故障实验 |
| TLS 校验被全局关闭，CORS 开放且未显式只监听回环 | `server.js`；extractor 也单独跳过证书校验 | 代码事实，不等于已确认公网可达 |
| BGM 为播放时叠加，未混入导出，也未做 Ducking | `public/app.js` 与 `audioMerger.js` | 代码事实 |

历史报告 `plan/fix-report-2026-09-18.md` 保留作为过程记录，不应视为当前全部问题已解决的证明：
- 「单句最坏约 60 秒」不能由当前依赖实现保证。
- 8 句样本不足以证明固定的 25% 挂起概率、网络黑洞根因或重试相互独立；`0.25^6` 不是可靠性保证。
- 原报告对 OPPO 内部实现的描述不能当作已验证架构。
- 未重新验证历史商业 TTS 价格、平台关系或“自然度最好”等排名，不纳入当前决策依据。

## 6. 通用验收规则

每批交付按以下模板报告：范围、改动文件、复现方式、测试命令与结果、实际验证环境、未验证内容、已知问题、回退方式、下一阶段依赖。

- 严格区分静态检查、mock 测试、真实联网调用和人工听感测试。
- 不把「请求成功」「JSON 合法」「生成文件存在」等同于内容可信或音频可用。
- 初期测试默认离线，用 fake Provider/fixtures；需要真实模型费用、发送私人正文、部署或更改安全边界时单独确认。
- 不在任何报告、截图或元数据中暴露 Key。对日志和错误中的凭据进行脱敏。
- 不删除历史播客、不覆盖用户文件、不自动发布；必要操作先确认。
- 无需引入 React/Vue、Redis、向量数据库或微服务。存储与任务执行选择满足单机恢复需求的最小方案。
